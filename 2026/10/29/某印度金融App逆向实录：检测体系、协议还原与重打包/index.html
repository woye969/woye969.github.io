某印度金融 App 逆向实录：检测体系逐个拆、协议全还原、重打包一条龙

发表于2026-10-29|更新于2026-11-02|逆向

声明：本文为授权安全评估的技术复盘，所有测试基于自有设备与测试账号。App 名称、厂商、包名/类名、so 名、域名、接口路径前缀、版本号及密钥材料均已化名或隐去。请勿将文中技术用于未授权场景。

最近接了个印度金融超级 App 的活儿，目标 DApp——某集团旗下产品，钱包 + 个人信贷 + UPI 支付 + 电商商城四合一。这种 App 的检测体系和协议是主要分析目标，本文把整个流程拆开讲：检测体系逐个拆 → 绕过（动态 + 静态双方案）→ SO 层指令级分析 → 协议还原 → 重打包。

工具链先列出来，后文全部围绕这套：

工具 用途
jadx 1.5.1 全量反编译
baksmali / smali 2.5.2 dex 手术
androguard + 自研注解解析器 312 个接口提取
capstone ARM64 指令级反汇编
Frida 16.7.19 动态插桩
mitmproxy MITM 抓包
uber-apk-signer 1.3.0 重签名

测试机：小米 8，Android 10，arm64，Magisk root + LSPosed。

一、样本：Split APK 拆包

原始样本是 Google Play 分发的 Split APK 容器（ZIP 壳），解出三件：

加固结论先行：没壳。 四重证据：7 个 dex 头全是标准 dex\n037；加固特征字符串（jiagu/libDexHelper/SecShell/StubApp…）扫描全部误报；Application 类是普通 Koin 启动无代理解密；Frida spawn 后类加载器直接可见全部业务类。

混淆结论：基本没混淆。 全包 51,744 个类，单字母混淆名只有 1,239 个（2.4%），且都是三方库 shrink 残留和 Compose lambda，App 自身逻辑 100% 完整命名，连 app_productionRelease.kotlin_module 都留在 META-INF 里把构建变体名卖了。R8 只做了 shrink+optimize，obfuscation 大概率被 keep 规则一锅端了。

这种体量的金融 App 不加固不混淆，后面的一切都是顺水推舟。

二、检测体系：从闸门到每一颗螺丝

2.1 闸门在哪：LauncherActivity

反编译后直接看启动页，检测逻辑一目了然（jadx 还原）：

三个要点：

  1. 检测只在生产环境生效（isAppProduction()），debug/UAT 包裸奔——这个开关同时控制后面讲的 RSA 公钥选型；
  2. 检测失败的动作只是 Toast + 发广播自杀，不写文件、不上报阻断标志，hook 空间巨大；
  3. onStart 重复检测一次，所以绕过必须覆盖两个生命周期点（用函数级 hook 天然覆盖）。

原理就是 File.exists() 的 TOCTOU 老套路——Magisk 的 mount namespace 隔离能让 exists() 返回 false，但只防得住不藏 su 的 root。

④ Frida 进程检测——自研检测里唯一有点意思的：

原理是枚举 /proc 下的进程名找 frida 守护进程。弱点和所有进程名检测一样：改个名就没了（florida-server、或者 frida 16 的 frida-server-16.7.19 都不含 fridaserver 子串）。更本质的 Frida 检测（扫内存 maps 找 gadget、检测端口 27042、检测 gum-js-loop 线程名）一个都没有。

⑤⑥⑦ Xposed 三连：

  • 调用栈检测（⑥）：原理是 Xposed hook 方法时会往栈里插 XposedBridge.handleHookedMethod 帧——但只在被 hook 的方法执行时检测才有效；
  • 包名检测（⑤）：de.robv.android.xposed.installer 是十年前的老包名，LSPosed 早就不用了；
  • metaData 扫描（⑦）是这台测试机上唯一真实命中的项：LSPosed 管理器 APK 的 metaData 里带 xposedmodule 键，被全量包扫描逮个正着。

2.3 RootBeer：第三方库打包送上

检测链里还挂了 RootBeer（com.scottyab.rootbeer），isRootedWithBusyBoxCheck() = 包名扫描（magisk/supersu/kingroot…）+ 二进制路径探测（走 native）+ ro.debuggable 等 dangerous props + /system rw 挂载检查 + test-keys + which su + Magisk binary。都是开源库标配，值得一提的是它还有个 detectRootCloakingApps()，专门扫 root 隐藏类 App 的包名。

五、SSL Pinning：唯一的 pin 在支付 SDK 里

主 API 的证书校验就是系统默认 TrustManager，无 pinning。App 自带的 CustomTrustManager 更有意思——checkServerTrusted 里按 isAppProduction() 分支，非生产环境完全不做任何校验，生产环境委托系统。

全包唯一的真 pinning 在某第三方支付 SDK 的混淆类里（CertificatePinner.Builder().add("<vendor>.com", [4×sha256])）。

重打包版三管齐下：

  1. networkSecurityConfig：注入 res/xml/nsc_trust_all.xml（trust system+user CA）——targetSdk 36 默认不信任用户 CA，这才是 MITM 的真正门槛，跟 pinning 没关系；
  2. smali 删掉支付 SDK pinning 构造块（48 行，删除前验证区间内无 label 引用）；
  3. CustomTrustManager.checkServerTrusted → return-void。

验证效果（mitmproxy + CA 装进 /data/misc/user/0/cacerts-added/ + adb reverse + 全局代理）：主 API/CleverTap/AppsFlyer/Firebase 全部解密成功，而系统进程（Google 服务、小米云）握手失败——bypass 精确只对目标 App 生效。

六、重打包流水线总结

重打包能成立的前提是把”重打包三障碍”逐一排掉：无壳、AssetValidatorActivity 只是资源加载测试（失败页还带 Continue）、无签名自校验（全包没有 GET_SIGNATURES 比对逻辑）。

七、收尾总结

维度 一句话结论
加固/混淆 全无。5 万个类明文全名
检测 Java 层四套全聚合在启动页单开关后；SO 层只有 RootBeer 原版；Frida 检测只认进程名字面量
协议 REST/JSON 全明文；登录 MPIN=Base64；转账 PIN=RSA；无防重放设计
SSL 主 API 无 pinning，靠 networkSecurityConfig 就能 MITM
重打包 无签名自校验，patch→重签→裸跑全通过

防御视角说两句：这种体量的金融 App，加固混淆是底线；登录凭证（MPIN）至少要 RSA/HMAC 绑定请求加 nonce 防重放；send-otp 必须加频控和号码预校验；检测逻辑别全塞在 Java 层启动页，native 多点校验 + 服务端风控二次确认才是正路——毕竟客户端的一切检测都只是提高成本，信任边界永远在服务端。

相关工具（Frida hook 脚本、smali patch 脚本、协议客户端）在整理中，后续视情况放出。
