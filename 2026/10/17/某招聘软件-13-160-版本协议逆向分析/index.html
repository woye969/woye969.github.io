某招聘软件 13.160 版本协议逆向分析

发表于2026-10-17|更新于2026-10-18

仅供学习交流与技术研讨，请勿用于任何未授权用途。文中敏感信息（手机号、令牌、设备指纹、密钥中段）均已脱敏；App 名称、包名、类名、域名均已化名。请遵守《网络安全法》及相关服务条款。

前言

第一次逆向国内的app，只敢逆个登录学习一下，如果app的开发者觉得有侵权请联系作者删除

目标是某主流求职 App（下称 TApp）。本文是Ro0t对其 Android 端 13.160 版本通信协议的完整逆向过程：从拆包、定位签名链路、啃 ollvm 混淆的 native 库，到纯算复现 sig/sp、自动化过滑块、真机对拍验证，最后完整走通协议登录。

整个过程断断续续花了两天（2026-10-11 ~ 10-12），静态分析为主、动态调试为辅，最终做到不依赖设备、纯 Python 发签名请求。

一、拆包与加固检测

APK 拿手第一步永远是摸壳。用加固检测工具扫了一遍：未加固，9 个明文 dex，省去脱壳环节

apktool 反编译后，先按经验猜关键词定位协议入口。思路是抓常见命名：

  • sign / signature / encrypt
  • HTTP 请求封装层
  • JNI 桥接类

很快锁定一条链：

几个关键角色：

类/文件 职责
net.tapp.base.m 公共参数拼装 + 签名分发
com.tkit.signer.a 签名桥（Java 侧薄封装）
com.tkit.signer.SignBridge JNI 声明，动态注册 native
mo/a.smali API 路径表（字段名 → 相对路径）
config/l.smali 签名豁免接口列表

二、Java 层：签名链路

m.c 在业务参数外追加公共参数：

参数 说明
curidentity 当前身份
v App 版本号
req_time 毫秒时间戳
uniqid 设备唯一 ID
client_info 设备信息 JSON（机型/系统/网络/oaid/did/tinker_id…）
app_id 固定值，签名之后才追加，不参与签名

m.e 做两件事：

  1. 排序明文：参数按 key 升序，k=URLEncode(v) 用 & 连接，空值输出 k=；长度超 5000 截断（用于 sig）。
  2. 调 native 算 sp 和 sig，豁免列表里的接口用空密钥签，其余用会话 secretKey。

这里有个经典小坑：Java 的 URLEncoder 和 Python 的 quote_plus 行为不一致——Java 保留 ~、会编码 *，Python 反过来。不硬对齐的话，带特殊字符的参数签名必挂。写脚本时按 Java 语义写了个 java_urlencode。

三、native 层：libsigner.so 与 ollvm

libsigner.so 用了 OLLVM 系混淆：导出表里一堆 .datadiv_decode* 符号（数据/字符串运行时解密），JNI 方法不用 Java_ 前缀导出，而是 RegisterNatives 动态注册。盐和 V3.0 前缀都在 so 内部加密存放，静态 grep 是搜不到的。

通过lief 解 ELF + capstone 反编译定位，识别出几个核心函数：

  • signature：sig 纯算
  • encodeRequest：sp 生成
  • encodePassword：登录密码编码
  • decodeContentBytes：响应解密

算法构件都是老熟人：MD5、RC4、LZ4、魔改 Base64。难点不在单个算法，在拼装方式和密钥来源。

四、协议核心：三件套公式

对拍验证后的最终结论（已脱敏）：

sig

注意前缀是 V3.0 字面量。94 条真机样本全部对拍通过。

sp（请求密文）

有个反直觉的点：Python 的 lz4 压缩输出和 native 字节级不同（编码器决策差异），但服务器只要求能解，sig 才是完整性校验——所以不必追求字节级一致。

encodePassword（登录账号参数）

流密码无 padding，密钥固定不受 secretKey 影响。

响应解密

响应头 content-encrypt: yes 时，body 就是 RC4(盐或secretKey) + 魔改Base64 裸解（客户端用自定义 accept-encrypting: 1 协商头开启）。部分响应还会带 SBlock 块头 + LZ4，解压即可。

secretKey 生命周期

  • 游客态：空 → 全部退化为只用内置盐
  • 登录响应在数据包裹字段里下发 secretKey，此后 sp 的 RC4 密钥、sig 的盐、响应解密 key 三处共用
  • 每次登录轮换

请求结构

网关 https://api-*.example.com/api/。最有意思的设计：POST 请求的 query string 里只有 sp、sig、app_id 三个参数，body 为空，业务参数全部藏在 sp 密文里。登录令牌走独立请求头（化名 tk）不走 cookie。

易盾类滑块自动化是整个项目里最花时间的部分，几个关键点：

  1. 全参数 URL 加载验证页，captchaId 等环境参数一个不能少；
  2. 等 onReady 后摘除 .yidun_cover-frame 事件罩 iframe，否则拖拽事件被吞；
  3. 缺口定位：背景图与拼图 sprite 差分 + Canny 边缘模板匹配，限定搜索窗防高对比干扰；
  4. 拖拽必须用 CDP 触摸事件（Input.dispatchTouchEvent），mouse 事件页面不认；
  5. JS 桥是 androidBridge[event].apply(null, data) 的多参数调用，令牌在 args[1]，Proxy 桥要捕获全部 arguments 才不丢数据。
