把 UPX 拆开：它怎么跑，魔改改哪里，脱壳怎么脱

发表于2026-10-20|更新于2026-10-20

UPX 是个压缩器，不是加密壳，更不是虚拟机。它把整个程序压成一坨数据，再附上一段会把自己解压出来的代码。程序启动时先跑这段代码，解压完、把导入表填好，再跳回原来的入口。upx -d 能一键还原，是因为它读文件里留下的一张 32 字节的头，不是因为它会把程序跑一遍。

魔改 UPX 的人改的就是这两样东西：要么改那张头，让 upx -d 不认；要么在解压代码前面再塞一层，让磁盘上的数据和运行时看到的数据不一样。看懂正常的 UPX 长什么样、入口在哪、原入口又在哪，这些改动就都有地方落。

下面以 win64 的 PE 为例。32 位的骨架一样，寄存器和地址宽度不同。文中的报错是对 UPX 5.0.0 和 5.0.2 做字节级破坏测出来的，两版行为一致。有些旧教程说“三个节名和版本串缺一不可”，那个结论是错的，后面会写到。

加壳前后，文件里有什么

一个没加壳的 PE 大致是这样：DOS 头，PE 头，节表，然后 .text、.rdata、.data、.idata、.reloc 这些节。入口点指向 .text 里的某条指令，导入表放在 .idata，告诉加载器该从哪些 DLL 取哪些函数。

UPX 把这些节（资源节有时除外）压成一块，再重写成三个节。

节 磁盘上 内存里 干什么
UPX0 没有内容，SizeOfRawData 为 0 一大片可读写可执行的空页 解压的目的地。原程序的节会在这里归位
UPX1 有内容 可读写可执行 版本串、32 字节头、压缩数据、解压代码
UPX2 有内容，通常一页 只读 壳自己的导入表

UPX0 和 UPX1 的 PointerToRawData 经常写成同一个文件偏移。这不冲突，因为 UPX0 的长度是 0，加载器不会从磁盘读它。看到“第一节虚拟上很大、文件里是空的，第二节紧跟着、可执行”，就可以怀疑是 UPX，节名已经不重要了。

有资源的程序会多留一节，常常还叫 .rsrc。不是整整三节，不代表它不是 UPX。

先把 PE 里几个词说清

不把这几个词分开，后面 EP 和 OEP 一定混。

文件偏移是字节在磁盘文件里的位置。十六进制编辑器里 Ctrl+G 跳的就是这个，前提是你选的是 hex offset，不是虚拟地址。

RVA 是相对于映像基址的偏移。节表里的 VirtualAddress、可选头里的 AddressOfEntryPoint，都是 RVA。

VA 是 RVA 加上映像基址。64 位程序基址通常是 0x140000000，开了 ASLR 之后每次加载都变。调试器里看到的地址是 VA。

三者的换算只在某一节内部成立：

第一节 SizeOfRawData 为 0 时，它没有文件偏移。这时候入口如果指向它，说明有人后来往这个空节里塞了东西，并把 PointerToRawData 改掉了。这是魔改，不是正常 UPX。

EP 是 AddressOfEntryPoint，可选头里的一个 4 字节 RVA。PE32+ 里它的文件位置是 e_lfanew + 0x28。e_lfanew 在文件 0x3C。普通加壳样本这个值是 0x80，所以 EP 字段在文件 0xA8。这是这套样本的数，不是所有 PE 的数。换一个文件先读 0x3C。

加载器创建进程之后，会从 EP 指向的那条指令开始执行。加壳之后，这个值被改成解压代码的位置，不再是原程序的 main。

OEP 不是 PE 头里的字段。文件里没有一个叫 OEP 的成员。它是原程序自己的入口，也就是没加壳时 AddressOfEntryPoint 的那个 RVA。UPX 把这个地址编进了解压代码末尾的一条跳转里，源码里的标签叫 original_entry，指令是 jmp original_entry。

32 字节的头

upx -d 的全部能力都在这 32 字节上。源码在 stub/src/include/header.S 和 src/packhead.cpp。win64 用小端。

15、16、17 在源码里标着还没启用。win64 不会出现大端那一组编号。

filter 不是加密。压缩之前，UPX 会把相对 call/jmp 的位移改写成更好压的形式，filter 字段记下用了哪一种。解压之后必须做逆变换，否则 call 的目标是错的，程序一跑就飞。只把压缩算法解出来、不做这一步，看起来像代码，运行必崩。upx -d 会做这一步。自己写解压器就得自己做。

格式编号里和 Windows 有关的：9 是 32 位 PE，36 是 64 位 PE，21 是 Windows CE。43 和 44 是 ARM64 的 64 位 PE，源码写明还没实现。头版本现在的样本基本都是 13，upx -d 接受 12 和 13。更老的 UPX 头只有 28 字节甚至更短，字段宽度不一样，别拿这张 32 字节的表去套 2000 年的样本。

解压代码跑起来之后

入口处那四条 push 之后，流程是固定的。

第一步，解压。NRV 或 LZMA 把数据写到 UPX0 的地址范围。写的是内存，不是磁盘上的 UPX1。所以调试器里如果在 UPX1 里找原程序的代码，找不到。

第二步，unfilter。按头里的 filter 把 call/jmp 变回来。

第三步，核对解压结果的 adler32。对不上就退出，不会跳到原入口。

第四步，重建导入表。这一步最值得看懂，因为动态脱壳最后修 IAT 就是在补它。

压缩数据里保存着原程序的导入信息。解压代码对每个 DLL 做一次 LoadLibraryA，对每个函数做一次 GetProcAddress，把返回的地址写进 IAT。源码里这段叫 PEIMPORT：先读 DLL 名，call [rip+LoadLibraryA]，再逐个函数 call [rip+GetProcAddress]，mov [rbx], rax 把地址填进去。某个函数没找到就走 ExitProcess 退出。

导入表瘦成这样，是比节名更硬的指纹。节名改起来是改 8 个字节。导入表要改，就得改解压代码。

第五步，VirtualProtect。解压过程中 UPX0、UPX1 是可写的。这一步把节属性改回原来的只读、可执行、可读写。源码里甚至会直接改内存中节表的标志位，把可写位清掉。所以在跳到 OEP 之前 dump，节属性可能还是可读写可执行，这不代表原程序本来这样。

第六步，重定位。UPX 的解压代码用 RIP 相对寻址，自己不怕 ASLR。原程序里的绝对地址需要按实际加载基址修正，这段在 PERELOC1。

第七步，TLS。如果原程序有 TLS 回调，UPX 会把回调换成自己的，等解压完成再去调原来的回调。标签是 PETLSC 和 PETLSC2。这一点和脱壳有关：TLS 回调比 EP 更早执行。作者要是把检查塞进 TLS，你在入口下断已经晚了。正常 UPX 自己也会占 TLS 回调的位置，所以有 TLS 不一定是魔改，要看回调指向哪。

最后，恢复寄存器，jmp original_entry。这条 jmp 的目标就是 OEP。

upx -d 到底查什么

它不运行解压代码，也不比对入口处的机器码。它在文件里找 "UPX!"，读那 32 字节，校验和过了就按 method 解压，再做 unfilter，写出原来的 PE。

我对一份正常的 win64 加壳文件逐项改一个地方，5.0.0 和 5.0.2 的结果一样。

改动 upx -d 的反应
不改 解开
"UPX!" 改 1 个字节 file is possibly modified/hacked/protected，加 --force 也没用
只改第一节的名字 同上
只改第二节或第三节的名字 照样解开
版本串 "5.02" 改掉 照样解开
"UPX!" 和第一节名字都改回去，版本串和其他节名保持乱的 解开
算法编号改了，校验和没重算 header corrupted 3
算法编号改了，校验和重算了，但数据和算法不符 compressed data violation
压缩数据改 1 个字节，头不动 checksum error
入口 RVA 改到别处 not packed by UPX
解压代码第一条指令改成 NOP 照样解开

这张表可以直接当分类器。

报 modified/hacked/protected，只看两处："UPX!" 还在不在，第一节名字是不是 UPX 开头。版本串、第二第三节名，这两个版本都不检查。旧教程说三处缺一不可，那是猜的。

报 not packed by UPX，它没在期望的位置找到头，或者入口不在它认为的解压代码上。先看 EP 落在哪一节。落在空节里，几乎一定是前面被加了一段代码。

报 header corrupted，32 字节自己的校验和没过。先算，再决定哪个字段被改了。

报 checksum error，头是自洽的，压缩数据和头里的 adler 对不上。数据被 XOR、被截断、被替换，都走这里。

报 compressed data violation，校验和过了，但指定的算法吃不下这段数据。算法编号是假的，或者长度字段是假的。

解出来的文件比头里记的原文件大，多出来的是 overlay。UPX 把最后一节结束之后的字节原样附在输出后面。有人把额外代码追加在文件尾时就会这样。overlay 不影响原程序运行。

还有一件事这张表说明了：解压代码被改、被加密、前面被塞了别的代码，只要头和压缩数据是真的，upx -d 就能还原原程序。这也是为什么能静态还原时就不要去调试器里 dump。

魔改实际在改什么

见到一个没见过的样本，先别改字节。看四样东西：节的形状还在不在，导入表是不是只剩那几个函数，upx -d 报哪一句，EP 落在哪、那里的指令是不是 53 56 57 55。然后它就归到下面四类里的某一类，或者几类叠在一起。

改指纹

这一类不碰压缩数据。程序照常跑，因为解压代码不靠节名和 "UPX!" 活着。upx -d 靠它们活着。

最常见的是把 UPX! 改成 UPY!，一个字节。搜 UPY!、UPZ!，或者到版本串后面 5 字节去看。改回 55 50 58 21。校验和不算 magic，不用重算。

只改第一节名字就够让 upx -d 失败。把那 8 字节改回 UPX0，后面补 0。节的 VirtualSize、PointerToRawData 不要动。

第二、第三节名和版本串，改了能躲过只扫字符串的工具，躲不过 5.0.x 的 upx -d。要文件干净就改回去，不改也能解。

这一类的判断标准很简单：把 "UPX!" 和第一节名字修好再跑一次。解开了，后面没有别的层。没解开，看新的报错，进入下面某一类。

在入口前面加一层

这一类让磁盘上的压缩流和运行时解压代码读到的不一样。upx -d 读磁盘，所以失败。进程启动时，EP 指向的一小段代码先把数据变回去，再跳进真正的解压代码。

这段代码几乎总是塞在 UPX0。UPX0 本来没文件内容，把 PointerToRawData 指到文件尾新加的数据，SizeOfRawData 设成对齐后的长度，加载器就会把它映射到那个节的 RVA。EP 再改过去。文件比正常加壳结果大出来的那一截，就是这段代码。

它要能跑，得满足两个条件，否则作者自己的程序也跑不起来：

位置无关。用 lea reg, [rip+disp]，不要写绝对地址。开了 ASLR，绝对地址一定指飞。

不破坏解压代码要的寄存器。解压器要 rbx、rsi、rdi、rbp，入口时也依赖进程刚创建时的现场。额外代码用 r10、r11 这种寄存器做循环，是常见的写法。用了 rax 又没保存，程序会在解压阶段崩，看起来像壳坏了，其实是这段代码把现场毁了。

还原不需要把这段代码跑一遍。它是数据变换的说明书。

反汇编 EP 指向的地方。找出三件事：算法、密钥、范围。算法大多是 XOR，偶尔是加、减、取反。范围从两条 lea reg, [rip+disp32] 算，目标地址等于下一条指令的地址加上 disp32。一条是起点，一条是终点。循环体是 xor byte 还是 xor dword，步进是 1 还是 4，决定你在文件上怎么做逆操作。

RVA 换回文件偏移，用前面的公式。范围经常从压缩数据的第一个字节开始，一直盖到解压代码的入口，中间的对齐字节也算在内。对齐字节漏了，解压代码对不齐，接下来报 checksum error。

XOR 的逆还是 XOR。加法的逆是减法。做完把 EP 改回这段代码最后跳去的地址，那就是真的解压代码。如果指纹也被抹了，按上一类改回去，再跑 upx -d。

密钥不一定是立即数。有的用几条算术算出来，在纸上算完还是一个字节。有的不是异或整段，只异或头，或者按 4 字节滚动。有的第一段代码先解密第二段，第二段再解密数据，要从 EP 顺着跳转读完，不能只读第一段。

循环里如果出现两个内存字节交换、下标对 256 取模，那是 RC4 一类。用 Python 把那段循环重放一遍，对文件做同样的操作。不必开调试器。

EP 被改到第一节之后，upx -d 的第一句是 not packed。它还没看压缩数据。所以这句报错不代表“不是 UPX”，只代表入口不在它期望的地方。

改头

头里每个字段都是给解码器用的。改法有两种，报错不同。

不重算校验和。最后一字节还是旧值，报 header corrupted 3。这是最好修的一种：字段改回去，旧的校验和自己就对上了。不知道原值就枚举。算法编号只有 2、5、8、14 值得试，每填一次就重算校验和。哪个不再报 header corrupted，留哪个。

重算了校验和，但字段是假的。upx -d 会真的用假算法去解，然后报 compressed data violation。这时不要再动校验和，改字段。

filter 被改了比较讨厌。解压能完成，逆变换用了错的参数，生成的程序一运行就崩。对 filter 那一个字节做同样的枚举，哪个解出来能跑哪个就是。

长度字段被改，不能拿 32 位整数去枚举。压缩长度可以从位置推：数据从 "UPX!" 之后 32 字节开始，到解压代码之前结束。解压代码的文件偏移用 EP 换算。如果 EP 已经被改去跑额外代码，就用那段代码最后跳向的地址。

adler 字段被改、校验和也配平了，解码能走完，最后报 checksum error。这种少见。先把算法编号枚举完，再考虑它。

动解压代码，专门对付调试器

upx -d 看不见这一层，因为它不运行代码。只要前面三层能还原，反调试不用管。它只在你选择“跑起来再 dump”时才存在。

写法 实际效果 动态时怎么处理
mov reg, gs:[0x60]，再读 +2 读 PEB 的 BeingDebugged。高明的写法不是崩，而是换一把错的密钥去解密，然后死在解压器里面，看起来像数据坏了 把读 BeingDebugged 的那条指令改成 xor reg, reg，让它以为没有调试器
导入表里多了 IsDebuggerPresent 或 CheckRemoteDebuggerPresent 同上，只是走 API 在返回时把 eax 改成 0

反调试很少单独出现。它总是和“入口前面加一层”叠在一起：先检查，再解密。静态把解密逆了，检查就变成不会执行的代码。

动态脱壳的几种走法

静态能解开就不要看这一节。下面是静态走不通时才用的，比如解码器被整个换掉，或者密钥要运行到一半才拼出来。

不管哪一种，先确认反调试不会在中途把密钥换掉或把进程杀掉。否则你等来的不是 OEP，是一次访问违例。

单步跟到那条 jmp

x64dbg 加载，从 EP 开始。正常 UPX 的解压循环很长，不要一条一条步过去。在循环后面、导入重建后面下断点，或者直接对 jmp 这种转移下断。

win64 的 UPX 离开解压代码时是一条 jmp，目标在另一个节里，通常落进 UPX0 的地址范围。那就是 OEP。目标如果还在 UPX1 里跳来跳去，还没到。

这条路最直观，也最容易被反调试和时间检测打断。

对解压目的地下内存断点

UPX0 的 VirtualAddress 就是解压目的地的起点。对那一页下内存写入断点，会在解压过程中反复断下，烦。等写入停了，再对同一区域下内存执行断点。解压代码跳到 OEP 时，会第一次从那片内存取指令，断点就断在 OEP。

这个办法不依赖你认不认 jmp 的机器码。解压代码被花指令搅过、不好跟的时候用它。

ESP 定律

进入 EP 时看栈顶，给那个地址下硬件访问断点。UPX 的解压代码开头 push 了四个寄存器，做完之后会 pop 回来，栈回到进入时的位置，然后才 jmp 到 OEP。硬件断点在 pop 完、即将离开的时候断下。再走几步就是那条 jmp。

这个办法对“开头保存寄存器、结尾恢复”的壳都有效，不限于 UPX。作者要是在中间改了栈，或者用了别的方式保存现场，就会失效。

等一个只有原程序才会调用的 API

原程序迟早要调用它自己的函数，比如这套练习里的 fgets 和 puts，一般程序里的 GetCommandLineW、MessageBoxA。在那个 API 上下断。断下时看返回地址，返回地址在 UPX0 的范围内，调用点附近就是原程序的代码。沿着调用栈往回找，能找到 OEP，但不一定正好断在 OEP 上。

这个办法适合解压代码搅得很乱、jmp 不好认的情况。它找到的是“原程序已经在跑了”，还要再往前收一点才能得到真正的入口。

用工具在 OEP 处 dump

到了 OEP，内存里原程序的节已经在 UPX0 那片地址上，IAT 里也已经是真实的函数地址。这时候 dump 才有意义。早了，dump 出来的是没解压的数据，或者 IAT 还是空的。

Scylla 挂在 x64dbg 里做这件事：对进程做 dump，再 IAT 搜索、Get Imports、Fix dump。修 IAT 能成功的前提是 IAT 里已经是 GetProcAddress 返回的那种地址。解压代码正常跑完就是这样。中间隔了跳板，Scylla 会把跳板当成 API，修出来的文件一运行就错。

pe-sieve 可以在进程外面扫被改过的页，适合解压代码会把 PE 头抹掉、Scylla 找不到模块的时候。它不是第一步该用的工具。

dump 出来的文件还要改入口。dump 工具有时把入口留成壳的 EP。可选头里的 AddressOfEntryPoint 要改成 OEP 的 RVA，不是调试器里看到的 VA。RVA = VA - 这次加载的实际基址。实际基址看模块列表，不要用 0x140000000 去减，ASLR 开着时那个数是错的。

这几种办法怎么选

入口处就是正常的 53 56 57 55，只是 upx -d 因为头被改了而不干活：不要动态。把头修好，或者自己按头里的长度解压。

入口处是一段解密，解密之后才是 53 56 57 55：优先在文件上做逆变换。逆变换需要的密钥要运行起来才有，再考虑动态。动态时在解密循环结束处下断，不要单步。

解压代码已经不是 UPX 的了：ESP 定律和内存执行断点仍然能用，因为它们不依赖 UPX 的指令。API 断点是兜底。
