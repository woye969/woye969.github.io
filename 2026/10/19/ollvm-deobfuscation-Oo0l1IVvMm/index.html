从 F5 按不下去说起：OLLVM 三板斧、jmp reg 地狱，和一个反混淆插件的诞生

发表于2026-10-19|更新于2026-10-19

引子

事情是从一道 CTF 题开始的。拿到一个 stripped 的 ELF，定位到 main，熟练地按下 F5，然后 Hex-Rays 给我看了这么一个东西：

就这么多。一个 48KB 的函数，反编译出来 700 字符，最后一行是裸的 jmp rdx。后面的几万字节代码在 IDA 里是一片灰色的未定义区域，不属于任何函数。

如果你也见过这个场面，那我们算是踩进过同一条河。这篇文章把这条河完整趟一遍：先讲清楚 OLLVM 的三种经典混淆 pass 各自在藏什么、业界怎么对抗；然后讲教科书上没有的那一章——把分发器本身也混淆掉的 jmp reg 变种，它是怎么被逆向清楚的；最后把这些东西做成的一个开源插件 Oo0l1IVvMm（https://github.com/woye969/Oo0l1IVvMm ），选个模式按 F5 就能看反混淆结果。

在动手之前得先明白一件事：反编译器为什么会被这种东西难住。

CPU 层面没有 if/else，没有 for，只有一串指令和跳转。反编译器的第一份工作是把指令切成基本块（一段只会从第一条进、从最后一条出的直线代码），块和块之间连成控制流图（CFG），然后在图上做结构化识别——发现两个块是”先进后出”的嵌套关系就还原成 if/else，发现有回边就还原成循环。这套流程有个天生的命门：每个跳转的目标必须静态可知。je 0x401748 没问题，目标就写在指令里；但 jmp rdx 的 rdx 是运行时才算出来的，反编译器看不到，于是一切到此为止——函数截断、后续代码不可达、结构化无从谈起。

所有的控制流混淆，本质上都是在围绕这个命门做文章。区别只在做得多规矩。

一、OLLVM 三板斧

OLLVM 不是某个具体工具，而是一类东西的统称：只要是在官方 LLVM 上叠加混淆 pass，都可以叫这个名字。最经典的是三个 pass：指令替换（sub）、虚假控制流（bcf）、控制流平坦化（fla）。除此之外还有字符串加密、间接跳转这些常见配料。

1.1 指令替换：把语义埋进位运算

sub 的思路很直白：把简单的算术运算，替换成一组数值上完全等价、但形式冗长晦涩的表达式。替换的产物通常长成 MBA（Mixed Boolean-Arithmetic，混合布尔-算术表达式）的样子——把普通算术和位运算搅在一起。

核心是一堆数学恒等式。比如异或，有这么一条：

于是一行 r = x ^ y; 混淆完变成 r = (x + y) - 2 * (x & y);。一行变一行看着不亏？实际编译出来是一条 xor 变七八条算术指令，而且这种替换是递归套娃的——混淆器会把替换出来的表达式再替换一遍，几轮下来一个异或能膨胀成上百条指令的位运算瀑布。

对抗：既然替换靠的是有限多条恒等式，那就模式匹配往回折叠。D-810 在这一项上是标准答案——它挂在 Hex-Rays 的优化流程里，内置了一百多条规则（Hackers Delight 系列、OLLVM 系列、Factor 系列等等），专门识别这些等价形状然后化简。对 D-810 处理不了的非标准 MBA，还有 GAMBA 这类基于求解器的深度还原工具。”D-810 初步清洗 + GAMBA 深度还原”是打硬仗时的标准组合拳。

对抗除了模式匹配还有个更取巧的路子：bcf 的不透明谓词经常放在全局变量里（通常未初始化，躺在 .bss 段）。静态分析器不知道它的值，但我们知道——混淆器生成它的时候就是要它恒假。那就手动给这个变量赋上定值，再把段属性改成只读，反编译器会触发常量传播，把死分支自动剪掉。改汇编直接 patch 也一样。这个技巧属于”利用敌人的编译器打敌人”。

1.3 控制流平坦化：拍扁一切

fla 是三个里面最重量级的。它干的事用一张图就能说清：

上面的原始 CFG 里，块 2 到块 3/4 是清晰的分支嵌套；下面的混淆后 CFG 里，所有块都被摘下来挂到同一个主分发器上，原来”谁跟谁有先后关系”的信息被完全抹掉，只剩”每个块执行完都回到分发器”。

要读懂平坦化后的代码，得认识它的六大组件（图来自腾讯安全那篇经典分析）：

  • 序言（Prologue）：函数入口，初始化状态变量，比如 state = START_KEY；
  • 主分发器：心脏，一个巨大的 while(true) 包着 switch(state)，读当前状态决定下一个执行哪个块；
  • 子分发器：复杂变种会嵌套多层 switch，或者用数学公式直接算跳转目标；
  • 真实块：原始业务逻辑，被隔离成 switch 的一个个 case，块和块之间不再直接相连；
  • 状态更新 / 预分发器：每个真实块结尾不跳下一个块，而是 state = NEXT_KEY 然后跳回主分发器；
  • 返回块：状态到达结束值时跳出循环。

执行流程就是：序言设 state=1 → 分发器跳到 case 1 → 真实块 A 干活、末尾 state=2 → 跳回分发器 → 再分发到 case 2……循环往复直到出口。

写出来的伪代码就是你熟悉的那坨 while(1) { switch(0x1971C07E) { case 0x84DB614C: ... ——状态常量全是四个字节都非零的高熵值，一眼望不到头。

对抗思路很朴素：重建真实块之间的直接边。块 A 结尾把 state 更新成了 K，而 state==K 时分发器会跳去块 B，那就把 A 的结尾直接改成 JMP Block_B，绕过分发器。所有真实块都这么连一遍之后，分发器没了入边，变成死代码，结构化识别自己就能把 if/else 和循环复原出来。

工具上，D-810 的 Unflattener、基于符号执行的 deflat（自动识别六大组件 → 从每个真实块符号执行到分发器、求解 state 值和对应目标块 → 直接 patch 二进制）、或者 Unicorn 模拟执行记录真实轨迹后修复，都是这条路。我们插件 MIN 模式的引擎组合（unflat + D-810）也属于这一派。

到这里为止都是教科书内容。下面的部分，教科书上没有。

二、jmp reg 家族：当分发器本身也被混淆

前面说的三种 pass 有个共同前提：分发器是规矩的。状态变量躺在寄存器或栈上，跳转目标查一张静态表， cmp 链或者 switch 长得明明白白。valrange 类工具（包括 D-810 的 Unflattener、hrtng、deflat）对付它们的原理都叫”值域传播”：算出每个块出口时状态变量的取值，和分发器入口处要求的取值配对，配上了就连一条直接边。

但定制混淆器不按这个出牌。它会把分发器本身也混淆掉——不再有集中的 dispatcher，查表逻辑被打散内联进每个块尾部，跳转表加密，连状态变量都藏进栈槽。我在一个 CTF 样本里遇到的就是完整形态。先看汇编，这是函数里几百个分发 stub 中的一个（地址 0x401230）：

整个函数里有 175 个这样的 stub，用 jmp +2 串成一条链：如果当前状态值不落在这个 stub 负责的区间，表项加密钥解出来的恰好是下一个 stub 的地址，于是继续比下一个阈值。等价于一条二分/线性比较链，但静态看上去就是几百个裸的 jmp reg 互相乱跳。

把这个协议完整逆出来之后，四样东西浮出水面：

组件 值/位置 说明
状态基值 0x19a4231a，函数入口单次写入 [rsp+0xc] 真实状态 = 基值 + 各块自己的偏移
解码密钥 r14 = 0x5825c6f0，全程不变 表项 + 密钥 = 真实目标
表基址 全局 qword_413090 → 0x1c843db4 数据段里指针套指针
stub 链 约 175 个，遍布全函数 每个 stub 比较一个状态区间

还有两个加料设计。其一，有 33 处 cmove %edx,%ecx——原始程序的 if/else 被折进了状态计算里，同一个汇合点的状态值有两个候选，哪个值对应哪个目标需要路径敏感的关联。其二，有 10 处 je 401230 这样的条件跳转直接跳进链头，条件和分发链搅在一起。

面对这种东西，值域传播类工具的表现如何？hrtng 的日志说得很诚实：

64 个配上了，88 个死了。死因就是前面说的三个坑，每一个都足以断链：

  1. 状态在栈槽。抽象解释器的内存模型很脆：任何一次”经未知地址的存储”（比如一个 call 之后状态就不可信了）都会把整个内存模型清掉。之后 mov ecx,[rsp+0xc] 读到的全是”未知”，后面全盘崩溃。
  2. 目标要经过算术解码。就算知道 ecx，目标 = 表项 + r14，表项 = 表基址 + 偏移，偏移还是个条件选择的结果。符号求值这条链，工具得把整个 stub 语义建模进去——而每个样本的 stub 还长得不一样。
  3. cmov 汇合。值域传播到汇合点会把两个候选值合并成一个集合，但”值 A 对应目标 X、值 B 对应目标 Y”这个关联恰恰在合并时丢掉了。丢掉关联，就没法重写。

三、换思路：别传播了，直接走

值域传播是”归纳法”——从入口归纳每个点的状态取值集合。对付 jmp reg 家族，我们换成”演算法”：对每个状态更新点，用该点具体的 (状态值， 密钥)，像 CPU 一样把分发序列逐条执行一遍。cmp 能定值就定值，查表能读就从文件镜像里读，密钥能算就加——直到 jmp reg 解出一个不是 stub 的地址，那就是这个状态的真实下一块。

听上去简单，落地时三个关键设计，每一个都对应前面一个坑：

第一，两遍分析 + 单写者常量槽。 先跑一遍完整抽象解释，找出”全函数只写一次、且写的是常量”的栈槽——本例就是入口处那句 movl $0x19a4231a, 0xc(%rsp)。然后第二遍分析时让这些槽变成”不坏金身”：内存模型被未知地址的存储清空时，这些槽自动复活。状态基值从此立于不败之地。（注意槽地址要用写入点自己的具体 rsp 算——这个函数序言是 5 个 push 加 sub rsp, 0x43c8，想当然地用入口 rsp 加偏移会算到十万八千里外。这是实际踩过的坑。）

第二，按值拆分走链。 cmov 汇合点的状态有两个候选值？拆成两次单值走链，各自落到各自的目标。拆完不但没有路径爆炸，反而顺手把原始 if/else 重建了出来——微码层在这类站点插一条 jz ecx, 值A → 目标A 的条件边，正好是混淆器当年折进去的那个分支。

第三，只重写有证明的边。 每个”直达边”背后必须是一次具体的静态执行：这个确定的状态值，经过确定的一串 cmp/查表/加法，落在确定的地址上。算不出来（比如表项加出来落到了数据段）就保守放弃，那个站点保留原来的分发路径。这有一个很好的数学性质兜底：抽象解释是过近似——就算拆分时多算出一个运行时永远不会出现的值，它对应的 jz 分支在真实执行里永远不命中，不改变程序语义。反过来”真实值不在集合里”才会出事，而这一点由过近似性保证不会发生（前提是内存建模完整）。

这套走链器在这个样本上的最终战绩：64 个链入口站点全部解析（63 个直接 jmp + 1 个落进链头），加上 10 个 je 站点共 74 个，其中 41 个单值站点改写为直达边、33 个汇合点做 jz 拆分。每一站都用 ELF 的原始表数据手工复核过——比如站点 0x401215：ecx=0x3de303b9，走 stub 链两次查表（0xa90 → 0x80 → 0x520 → …），最终落在 0x4021A9，与走链器输出一字不差。

微码层的三个深坑

在 Hex-Rays 微码层做重写（而不是像 deflat 那样 patch 二进制）好处是不动原文件、跟着反编译器优化走，但坑也深得多。三个印象极深的：

坑一：插块会重排编号。 微码块有 serial 编号，insert_block 会让后面所有块整体移位。最初的实现是边插块边写跳转目标，结果先写好的目标被后面的插入操作悄悄挪到了错误的块上——表现就是死活删不干净的分发链残留。修复是改成严格两阶段：先把所有要插的新块全部插完，再用最终编号统一写 goto/jz 指令和边。

坑二：成熟度 0 的边不可信。 microcode 回调触发时（maturity 0，刚刚生成），直达 jmp 并不会物化成 m_goto 指令——控制流就是”边”本身；而此时 mblock.succset 读出来还可能是空的。旧后继得自己从反汇编层的跳转目标推导，改写指令操作数要用 erase() + make_blkref() 重建（直接给 .b 赋值会被 IDA 的条件检查拒掉）。

坑三：可达集不会重算。 flowchart 阶段被标记可达的块，后面优化时 Hex-Rays 不会自动重算可达性。我们的重写把分发链全部架空之后，链本身成了死代码——但 Hex-Rays 照样渲染它，switch 一个不少。第一次尝试在 maturity 0 调 remove_empty_and_unreachable_blocks()，直接把整个函数删空了（伪代码剩 59 字符），因为那个阶段块的边关系还没建好。正确位置是 glbopt 阶段：那时边关系成熟，死链真的死透了，删之。

四、最重要的一课：假阳性比失败更可怕

必须单独开一节讲这个，因为它是整个项目里最险的坑——险在它不会报错，还会庆祝。

项目早期我们拿到过一次”完美”结果：一个被平坦化的函数，F5 输出从 98KB 降到 2.2KB，while=0 switch=0 goto=0，指标全绿，看起来反混淆圆满成功。这个数字甚至写进了早期 README。

真相：那次测试走的是批处理路径，Hex-Rays 钩子根本没装上（没有 UI，定时器不触发），函数在第一个未解析的 jmp rdx 处被截断，后面所有代码因不可达被 Hex-Rays 当死代码丢弃了。剩下的入口代码恰好干净——看起来像反混淆成功，实际是”内容全部丢失”。指标全绿是因为统计的是丢弃后的残骸。

所以后来给插件加了一条铁律：批处理 decompile() 和 GUI F5 必须走同一条恢复链；判断成功不看 switch 数量，看真实业务逻辑是否可见——原始常量、输入比较、函数调用，这些才是内容还在的证据。

五、Oo0l1IVvMm：把这一切做成一个插件

上面所有东西最后收敛成了一个开源插件：https://github.com/woye969/Oo0l1IVvMm（MIT，IDA Pro 9.x + Hex-Rays x64，Capstone 随插件带）。

设计上有两个刻意的决定。

第一，不做成全自动。 反混淆引擎挂多了必然拖慢每一次 F5——对没被混淆的函数纯属浪费。所以插件默认完全静默：不选模式时，F5 就是原生 Hex-Rays 的速度，导航也不触发任何分析。想用时在 Edit → Plugins → Oo0l1IVvMm 选一次模式（或按 Ctrl+Shift+Alt+D 弹选择框），之后 F5 自动走恢复链；再选 OFF 解除武装。

第二，按形态分工，不让引擎打架。 三个控制流重写器同时跑一个微码数组会互相破坏，所以两个模式是这样划的：

模式 针对的形态 引擎组合
MIN 经典 OLLVM 平坦化（三板斧里的 fla，中央分发器） 截断修复 + unflat（valrange）+ D-810 指令级简化（177 条规则：MBA/常量折叠/不透明谓词/Z3），走链器关闭，轻量
MAX jmp reg 内联编码表分发（第二节的变种） MIN 全部 + 具体走链解析 + 微码直达边/jz 拆分 + 死链删除

其实就是本文第一节和第二节的映射：三板斧交给生态里现成的成熟引擎，插件负责编排和冲突防护（比如 D-810 的 profile 选择在编排后自动恢复原值、检测到用户自己开了 D-810 GUI 就让位）；魔改变种用自己的走链引擎。

MAX 模式在参考样本上的实测：

指标 原始 F5 插件 F5
伪代码长度 98,390 字符 2,965 字符
switch（分发器） 175 0
goto 131 0
JUMPOUT 多处 0

这次是真的干净：恢复出来的代码有 8 次循环的函数指针解密、带完整参数的调用、原始阈值比较——是能读懂的业务逻辑，不是丢弃后的残骸。

还有一类连 MAX 都静态解不了的

后来又遇到一个 client/server 成对的样本。这次的分发协议里，密钥是函数的输入（mov ebx,[rcx]），表基址指针在文件里是密文，表槽内容干脆不存在——全部运行时（登录交互之后）才解密构建。我做了三重验证：基址指针 77 处引用全是读、零写入；表段文件里全零；静态反解出来的”指针族”确实能被一个固定 XOR 密钥解成干净地址，但解出来的目标指向运行时堆块，文件里没有内容。静态层面，神仙难救。

v1.1 给的答案是运行时快照：用 IDA 调试器跑到表已构建的时刻（题目自带的调试脚本会提示你该断在哪），一键导出内存段+寄存器，插件加载快照后用运行时内存覆盖文件镜像、用捕获的密钥钉死分发变量，MAX 走链照常工作。resolve_chain(seeds=..., mem_overlay=...) 也开放了编程接口。

（附赠一个和混淆毫无关系的排查故事：那个 client/server 对怎么都连不上，双向”connect/bind failed”。折腾半天发现是端口 5566 落在 Windows Hyper-V 的保留端口范围 5485-5584 里，bind 直接被拒。把两个二进制里的端口常量 0x15be 补丁成 25566 才跑通。逆向路上，一半的时间都花在这种地方。）

尾声

回头看这条线：三板斧各自有成熟的对抗工具，没什么新鲜的；真正值得写的是 jmp reg 家族逼出来的思路转换——从”归纳每个点的状态取值”到”用具体值重放分发序列”，以及每一条重写的边背后都要有一次可复核的静态执行。

几条原则，也是这个插件一直守着的：

  • 能静态证明的边才重写，证明不了的保留原状——宁可丑，不可错；
  • 一条假边比一百个 switch 更危险，因为伪代码看着正常、语义是错的；
  • 看到”干净得可疑”的输出，先怀疑是丢弃假象，再庆祝；
  • 判断成功的唯一标准：真实业务逻辑（原始常量、输入处理、函数调用）可见，且和二进制里的数据对得上。
