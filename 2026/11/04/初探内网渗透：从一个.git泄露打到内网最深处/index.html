初探内网渗透：从一个 .git 泄露打到内网最深处

最近在补内网渗透这块的知识，光看文章不过瘾，就找了个模拟企业内网的环境练手。整个环境是这么搭的：对外只暴露一个公司官网，后面藏着一套典型的微服务全家桶——配置中心、制品库、业务服务器、SSO 单点登录、代码仓库，一共埋了十个 flag，目标很纯粹：从那个官网进去，把内网翻个底朝天。

断断续续打了两天，中间有快一个小时卡在一个反序列化利用上动弹不得，最后那段的排查过程反而成了这次收获最大的部分。把完整的思路和踩的坑都记下来。

（文中公网 IP 打了码，flag 只留前几位；环境是自建靶场，仅供学习记录。过程一半在浏览器里确认页面变化，一半在终端里发请求，配图是我自己复现时截的，边打边补。）

前置知识

后面会反复用到的概念，先在开头铺一遍，只讲”是什么、为什么能被利用”，细节都在正文对应的位置。都熟的话直接跳过这节。

.git 泄露：网站用 git 管理源码时，项目根目录会有个 .git/ 目录，存着全部源码和提交历史。它一旦能通过 HTTP 访问，就等于源码公开。git 把每个文件按内容哈希存成 objects/ab/cdef... 形式的压缩对象，只要拿到 commit 哈希就能递归还原出整个仓库。

路径穿越：程序把用户输入拼进文件路径时（比如 path.join(目录, 文件名)），输入里的 ../ 会让保存位置跳出预定目录。本质是”字符串拼接”和”路径语义”之间的缝隙。

SSTI / 模板注入：Web 模板引擎（本文是 Node 的 EJS）的工作方式是把模板文件编译成代码再执行，<%- 表达式 %> 里包的不是要显示的文本，而是要运行的 JS。所以”能控制模板文件的内容”，约等于”能在服务器上执行代码”。

Java 反序列化：Java 序列化字节流里写着对象的类名，反序列化时服务端照着类名实例化对象。如果没有类白名单，攻击者可以投递构造好的”对象链”（gadget chain）：实例化过程中自动触发的方法一环扣一环，最终走到 Runtime.exec() 执行命令。Hessian 是其中一种二进制序列化协议，有自己的一套 gadget 生态。

内存马：不落地的 webshell。传统 webshell 是一个文件，删文件就除马；内存马把恶意逻辑注册进应用的运行时（比如 Java Web 的 Filter 链），只存在于进程内存里，没有文件可删，进程不死马就不死。

特权容器与逃逸：容器靠 namespace 和 capabilities 做隔离，普通容器里的 root 是”阉割版”；privileged 模式什么都不裁剪，宿主的磁盘设备直接可见——把宿主分区挂载进来就能读宿主文件，这是最朴素的文件级逃逸。

垂直越权：认证回答”你是谁”，授权回答”你能干什么”。接口只校验了登录态、没校验”这条数据是不是你的”，低权用户改个参数就能干高权角色的事。

SSO 与反向代理认证：单点登录让”在一处登录，处处免登”。常见实现是身份源登录后 302 跳到目标系统，URL 上带着身份信息；目标系统前面的反向代理校验后把身份写进请求头，后端应用无条件信任这个头——头里写谁，你就是谁。

第一步：信息搜集，先别急着扫

拿到一个网站，我现在的习惯是先别上来就扫目录。先把页面从头到尾看一遍——三个页面（首页/产品/关于）全是静态内容，前端 JS 也就是些滚动动画，没有任何攻击面。倒是 404 页面文案有点意思：「请求的资源未找到或尚未授权访问」，暗示存在隐藏端点。

然后再上目录字典扫。字典里我专门放了 .git/HEAD 这种”标准探针”——如果网站用 git 管理代码又没把 .git 目录排除在 Web 根之外，这个路径会返回 200。扫完就命中了两个：

浏览器里看一眼这个 404 页，文案里那句「或尚未授权访问」在我当时看来基本就是明示了。

第二步：手写 dumper 还原源码

.git/HEAD 返回 ref: refs/heads/master，但去拉 refs/heads/master 却是 404——loose ref 文件不在。这时候很多人就卡住了，其实还有一条路：.git/logs/HEAD（reflog），里面记录了每一次 commit 的完整哈希：

拿到 commit 哈希，剩下的就是纯体力活。git 的对象存储结构是 objects/<哈希前两位>/<余下 38 位>``，内容 zlib 压缩，解压后开头是类型标记（commit/tree/blob）。commit 对象里写着根 tree 的哈希，tree 对象里是一堆「模式 + 文件名 + 子对象哈希」的三元组，递归拉下来就能把整个仓库还原。

现成工具（GitHack、git-dumper）当然能用，但我建议自己写一遍，三十几行 Python，写完你对 git 内部结构的理解会上一个台阶。最后还原出 17 个文件：Express 入口、路由、EJS 模板、Dockerfile、docker-compose……

源码到手之后不是逐行看，而是带着模式去找。很快在 routes/admin.js 里命中：

files.logo.name 就是 multipart 包里客户端填的原始 filename，formidable 1.2.6 对它不做任何处理。path.join 也不做什么安全检查，只是字符串拼接加规范化——所以 filename 填 ../../views/index.ejs，保存路径就穿到了应用目录。

到这里我有了一个任意文件写。但任意文件写本身不等于 RCE，关键问题是：写到哪个文件、怎么让它被执行？

我一开始的念头是覆盖路由文件，转念一想就否了——require() 在进程启动时已经把 JS 加载进内存，改磁盘文件不重启不生效，而这个环境里我没有重启通道。反过来想：哪些文件是运行时会被反复读取的？EJS 模板。EJS 渲染的时候会把模板内容编译成 JS 函数执行，而且每次访问页面都重新读磁盘。所以覆盖 views/index.ejs，访问首页，模板内容就变成了我要执行的代码。

这就是任意文件写升级成 RCE 的那座桥：挑运行时会重读的文件下手。

EJS 模板里拿不到 require，但 process.mainModule.require 可以绕出来。上传这一步在终端里 curl 完成，文件名填 ../../views/index.ejs；然后切回浏览器刷新首页，flag{6bfe024f...} 直接渲染在页面上。第一个 flag 到手，同时我也拿到了容器的 root shell——后面所有内网操作都从这个”跳板”发起。

整条链一句话概括：通过源码审计找到上传接口，利用文件名未过滤的路径穿越覆盖首页模板（模板注入），实现 RCE，然后回浏览器访问官网确认结果。

顺带一提，环境还在 .git 里留了个彩蛋：docker-compose 注释里写着第一关容器故意不给特权，逼你往内网走。

第五步：Jraft 反序列化，卡了我一个小时的地方

Nacos 2.x 的集群节点之间用 JRaft 协议同步数据，端口 7848。这个端口的 WriteRequest.data 字段用 Hessian 反序列化，而 2.2.0 版本没有类白名单——标准的 Java 反序列化利用面：字节流里写着类名，服务端照着实例化，配合 gadget 链最终走到 Runtime.exec。

GitHub 上有现成的利用工具（NacosRce），下载回来，按 README 跑——

没有任何反应。 服务端返回的错误永远是同一句：No enum constant com.alibaba.nacos.consistency.DataOperation.

这时候排查思路很重要，我按顺序排了三种可能：

第一，是不是我参数写错了？ 把三种参数格式都试了一遍，错误一模一样。排除。

第二，是不是工具和目标环境不兼容（JDK 版本、Hessian 版本）？ 这个没法凭空猜，得搭本地复现。我在跳板容器里装了 JDK 8，把工具 jar 拿 CFR 反编译，看它到底怎么构造 payload——工具内置了 payload 生成类（HessianPayload），我直接调它的方法生成 payload 字节，再用和目标一样的 Hessian 版本（4.0.63）在本地反序列化。本地完美触发：Xalan 的 Process._main 被调起，Runtime.exec 执行了我预置的命令。说明 payload 本身没问题。

第三，那就是目标的执行流程跟我以为的不一样。 这一步用了个很有效的技巧：差分探针。给目标发四组内容完全不同的请求——纯字符串、一个目标上根本不存在的类、gadget 本体——如果目标真的走到了反序列化，这几组的报错应该各不相同；结果四组的响应一字不差。结论：执行根本没走到反序列化，在更早的地方被拦下来了。

这一段排查下来，我总结出一个套路，以后遇到”公开工具打不通”都适用：

  1. 先排除自己参数问题（多试几种格式）；
  2. 本地 1:1 复现——同版本 JDK、同版本依赖库，本地能触发就证明 payload 没毛病，差异在目标；
  3. 差分探针——发几组”预期报错不同”的请求，如果响应一模一样，说明执行在更早的地方短路了；
  4. 回去读目标版本的源码对执行顺序；
  5. 补上工具没做的部分。

SSO 平台用普通账号登录。这个环节的知识点一句话就能说完：认证回答”你是谁”，授权回答”你能干什么”，很多应用只做了前者。

第九步：SSO 信任链，谁能设那个头谁就是上帝

超管的 dashboard 上挂着系统列表，点「Gitea 代码仓库」会触发单点登录。这里我建议不要真用浏览器点，用 curl 跟一遍 302：

一眼就能看懂信任模型：SSO 侧把用户名和角色明文放在 URL 上，Gitea 前面的 sidecar 校验 role 之后发一个 sso_auth cookie，之后所有经过 sidecar 的请求都会被注入 X-Webauth-User: system 头，而 Gitea 开了 reverse-proxy 认证模式——无条件信任这个头，头写谁就登谁。

所以这一关的本质是：拿到超管会话 = 能领取 Gitea 上的任意身份。实际打三步：带 system 会话请求跳转拿 callback（token 就在里面），访问 callback 收 sidecar 发的 cookie，带 cookie 读私有仓库。中间还闹了个小乌龙：第一次只带 token 去 callback，sidecar 直接回 400——校验参数不全；把 username 和 role 补齐才 302。这个 400 反而把校验逻辑演示得明明白白。

最后带着 cookie 读 system/infrastructure 私有仓库里的 secrets/flag.txt：flag{04f4df55...}，flag#10，收官。十个 flag 齐了。

收尾与还原

打完把官网首页模板用 git 对象里的原版覆盖回去（还是同样的穿越通道），验证 title 恢复正常；nacos 那边卸载挂载、清理临时文件。唯一的遗留是注入的内存马驻留在 Nacos 进程里，声明重启也存活，彻底清除得重建容器。

三点收获

一、凭据链是内网渗透的主旋律。 回头看整条链：application.yml 给了 Nacos 弱口令，Nacos 配置里翻了 MySQL 凭据，宿主机 config.txt 给了 Nexus 账号，jar 反编译给出 SSH 密码算法，SSH 配置里翻了 SSO 账号，SSO 超管会话换来了 Gitea 身份。每一关的钥匙都在上一关的抽屉里，内网渗透做的就是不断找”下一个凭据”。

二、任意文件写要挑”运行时会重读”的文件。 模板每次渲染必读、配置每次连接必读，覆盖即生效；启动期加载的代码改了等于没改。这个判断直接决定了文件写能不能升级成 RCE。

三、工具打不动 ≠ 打不动。 这次最花时间也最值钱的就是 Nacos 那段：本地 1:1 复现证明 payload 无误、差分探针定位执行短路点、读源码对出校验顺序、最后补上工具漏掉的字段。公开工具永远滞后于环境，会排查比会收集工具重要得多。

附：环境上踩的几个坑

都是些跟渗透无关但很磨人的环境问题，一并记了：

  • Windows 下有好几种 shell，行为差异巨大。PowerShell 里裸 curl 是 Invoke-WebRequest 的别名，curl 参数全不认，要用 curl.exe；echo x > file 默认写 UTF-16 编码，写文本模板会坏，得 Set-Content -Encoding ascii。
  • WSL 很好用，但内网地址从 WSL 直连不了（没有路由），别在本地环境里直接 curl 内网——这不是命令错，是命令发错了层。
  • 交互式 bash 里双引号包着 ! 会触发历史展开（event not found），set +H 或者改单引号。
  • 引号嵌套是永恒的麻烦：命令一层套一层时，内层单引号会截断外层单引号，& 还会把半条命令扔进后台。我的解法是把内层命令 base64 编码后中转，容器里 base64 -d | sh 执行，从此告别转义。
  • WSL 里写脚本别放 /mnt/c 下，Windows 编辑器会给你写 CRLF 和 UTF-16，放 ~ 下省心。
