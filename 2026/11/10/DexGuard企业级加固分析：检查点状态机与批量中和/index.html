DexGuard 企业级加固分析：检查点状态机、API 隐藏与批量中和

发表于2026-11-10|更新于2026-11-10|逆向

声明：本文为授权安全评估的技术复盘，基于自有设备与测试环境。目标 App 名称、包名、路径、凭据均已化名或脱敏（下文统一以”目标 App”指代，包名以 com.<vendor>.app 指代）。仅供学习交流，请勿将文中技术用于未授权场景。

最近分析了一个用 DexGuard 做企业级加固的海外银行 App。这套东西跟国内传统壳的思路完全是两条路，值得单独写一篇。先把结论放前面：DexGuard 不加密 dex，它把防护做进了代码本身——检查点撒在全 app 四万多个类里，脱壳这个词在它面前失效了，因为根本没有壳。

传统壳 vs DexGuard

先介绍传统的壳（360，爱加密，梆梆这种）：

DexGuard 加固（从目标 App 实测）：

传统壳的防护在文件层加密 dex，DexGuard 的防护在代码层，在代码里面植入检查点。传统的壳在运行时 dump 下来然后就没事了，DexGuard 脱壳之后还得逐个拆检查点。

怎么判断是哪种

检查点状态机

DexGuard 的核心就是检查点状态机。

第一步：计数器自增混淆

这就是 DexGuard 的反分析设计，简单来说：

  • 正常执行时，计数器值满足特定的数学关系 → 奇偶性 = 0 → 走合法路径
  • 检测器发现异常时，会额外增加计数器值 → 奇偶性翻转 → 走处决路径
  • 你不可能静态分析出哪个分支是”处决”——因为那取决于运行时的计数值

第二步：奇偶分支路由

注意：不同检查点的方向不同！有的是 if-nez，有的是 if-eqz。这是故意的——防止你写一个通用的”跳过所有 if-nez”补丁器。

第三步：处决原语（自杀方式）

DexGuard 用 9 种不同的方式杀进程。每个检查点随机选一种：

# 原语 smali 模式 效果
1 巨型数组分配 new-array v0, vHuge, [I OOM 闪退
2 除零字面量 div-int/lit8 v0, v1, 0x0 ArithmeticException
3 恒零除法 (x-1)*x % 2 结果必为 0 作除数 同上
4 const-0 除法 const v0, 0x0 + div-int/2addr 同上
5 throw-null const/4 v0, 0x0 + throw v0 NullPointerException
6 hashCode-null const v0, 0x0 + invoke hashCode + throw 同上
7 NSE 构造抛出 new NoSuchElementException + throw 同上
8 状态对比较 if-ne state[A], state[B] → kill block OOM / throw
9 垃圾 Toast Toast.makeText(null, 垃圾ID, 0).show() 资源找不到异常

要点：每个被 DexGuard 处理过的类都有这两个计数器字段。所有检查点都读写它们。

nop = 空操作指令（什么也不做）。两行 nop 替换了原来的 if-ne 分支指令（每条 if-* 指令占 2 个字节 = 2 条 nop）。

5. 字符串解密函数

为什么要解密字符串：如果字符串是明文，静态分析直接 grep 就能找到 getPackageInfo、ZipFile 等敏感调用。加密后你只能看到一堆乱码 char 数组。

API 隐藏（ClientTransaction 机制）

DexGuard 把所有敏感 API 调用（PackageManager.getPackageInfo、ZipFile 构造器、Field.get 等）都藏起来了。

计数器毒化机制（检测 → 处决的桥梁）

这是最精妙的部分。DexGuard 的检测器本身不直接杀进程——它只是修改计数器的值，让后续检查点的奇偶性翻转，从而走到处决路径。

补丁策略

为什么不能只修几个关键点

因为检查点撒在全 app 的 42,822 个类、34,228 个文件 里。登录路径上就涉及几十个类。你修完一个，下一个又崩。

为什么按模式批量修是可行的

DexGuard 生成的检查点代码有高度一致的模式。按处决原语族分类后，每族写一个匹配规则：

补丁族清单

  • 除零字面量 0x0→0x1 — patch → 替换常量
  • const-0 寄存器除法 — patch → 替换为 const
  • throw-null — patch → 替换为 return
  • hashCode-null — patch → 替换为 return
  • NSE 构造+抛出 — patch → 替换为 return
  • 检查点分支 NOP — patch → NOP 两行
  • 恒等式除法 — patch → NOP
  • rem 误伤回滚 — patch → 恢复原指令

收尾

复盘下来，DexGuard 和传统壳的根本区别就一句话：传统壳的防护是”文件锁”，撬开锁就进屋了；DexGuard 的防护是”满屋的绊线”，房子本来就开着门，但你每走一步都可能触发处决。对付它没有脱壳捷径，只能靠模式识别把检查点成族地中和掉——好在它的生成器是模板化的，模式高度一致，这也是按规则批量 patch 能成立的全部前提。
