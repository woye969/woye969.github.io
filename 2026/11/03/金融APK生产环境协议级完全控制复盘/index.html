从一个 90MB 的金融类 APK 到生产环境协议级完全控制 —— 完整逆向实战复盘

发表于2026-11-03|更新于2026-11-03|逆向

声明：本文基于一次已授权的移动应用安全评估项目整理。目标应用已做匿名化处理（下文称 “App X”），所有真实域名、密钥、用户数据均已脱敏或泛化。技术细节保留完整，仅供安全研究学习，请勿对未授权目标复现。

0. TL;DR

目标是款预付卡/钱包类金融 App（化名 App X）。从头到尾干下来，结果如下：

  • Java 层 16 项安全检测全量绕过（root / Frida / Xposed / 签名校验 / 调试器 / 模拟器 / VPN / USB 全家桶）
  • 重打包出”检测免疫版”：无需任何注入工具，裸机通过全部检测进入业务界面
  • so 层五层排雷证明无 native 防护（直到机器码级 svc 指令扫描）
  • 生产环境协议级登录 + 流水 + 余额 + 交易详情全链路打通（真实账号、真实数据）
  • 顺手挖出一堆问题：客户端硬编码 PIN 加密密钥（ZPK）、列表接口加密而详情接口明文的加密策略不一致、UAT 环境万能 OTP、24 小时登录频控、单活跃会话语义

下面按实际干活顺序写，踩过的坑都留着。

1. 侦察与解包：先搞清楚手里是什么

拿到的是 .apks 分发格式（base + arm64 split + density split）。解完包先回答三个问题：

有没有壳？

我判壳从来不信单一证据，四条链交叉着来：

  1. dex 结构：4 个 classes.dex 全部可被 jadx 直接反编译，无加密 dex、无内存加载痕迹
  2. Manifest 入口：Application 类是业务自己的类，不是任何商用壳的 Stub（360 的 com.stub.StubApp、梆梆的 SecShell、爱加密等特征逐一比对）
  3. so 文件清单：全部为第三方官方组件（MLKit 条码、Mapbox 地图、AndroidX Camera、libc++_shared），无 libjiagu/libDexHelper/libnesec 等壳 so
  4. 字符串扫描：4 个 dex 对 jiagu/qihoo/SecShell/dexhelper/bangcle/ijiami 等关键字零命中

**没壳，就一层 R8。**省了脱壳的活，直接上 jadx。

APK 结构完整性

顺手把 zip 层也过了一遍：6497 个条目无重复、无路径穿越、无 overlay 载荷；4 个 dex 的 magic + adler32 + CRC 全部校验通过；无 DexClassLoader / System.load 动态加载；Class.forName 仅 1 处（业务相机）。

样本溯源

还有步很多人不做的：先确认手里这份样本没被中间人改过。拿 APK 实际签名证书的 SHA-256 去和 BuildConfig 里硬编码的指纹比（这 App 运行时也做这个校验）——逐字节一致，证书是 Play App Signing 签的。样本没被动过，可以放心分析。

2. Java 层检测体系还原

检测代码全在主 dex，三层结构：

搞笑的是 Frida 检测就俩招：连 27042 端口、查几个包名。换个端口直接瞎。Play Integrity 的依赖倒是打进包里了，代码里压根没调——枪都买了没上膛。

策略矩阵与执行流

场景策略是 MANDATORY/NON_MANDATORY 规则列表。LOGIN 场景强制 11 项；PAYMENT 场景额外加 INSTRUMENTATION_TOOLKIT 和无障碍检测。执行器逐条跑，任何 MANDATORY 命中 → 全屏 Compose 弹窗拦截，按钮跳系统设置让用户”修复”。

一个 QA 后门

还原参数传递时发现：登录页把”输入的手机号是否等于某硬编码号码”作为参数传给检测入口，命中则跳过全部检测。这个号码是厂商自己的测试号——典型的商店审核/QA 后门，也是个大乌龙：任何知道这个号的人在自己手机上可以跳过该应用所有本地防护。已提交厂商。

3. so 层：五层排雷做到机器码级

so 看着都是官方货，但”没看到坏东西”和”证明没有坏东西”是两码事，我分五层验：

  1. 符号表：7 个库全部导出函数枚举，不存在任何指向宿主包名的 JNI 方法——App 自身零 native 代码
  2. 字符串：全量扫描无 ptrace/TracerPid/反调试特征（mapbox 库里扫出的 “frida”/“xposed” 命中经上下文验证是压缩数据的随机噪声）
  3. 导入表：仅标准 SDK 的 dlopen/dlsym/prctl/mmap
  4. 编译特征：全部 RELRO 开、无 RWX 段、无 ollvm 混淆痕迹
  5. 机器码级：用 capstone 对全部 .text 段做线性反汇编——svc 指令总数为 0，并对全部 .init_array 回调逐个反汇编验证

第 5 层是底牌：arm64 上想绕过 libc 干隐蔽勾当（藏 ptrace、inotify 反调试）必须用 svc 指令，svc=0 就是说这些路根本不存在。”so 没问题”这句话从猜变成证。

结论：防护面 100% 在 Java 层。这个判断决定了后面所有绕过方案的成本——一层 Frida Java hook 就够，不需要碰 native。

4. 检测绕过：两条路线都打通

路线 A：Frida 动态绕过

三个动作：单点拦策略执行器（直接 return 一个”全通过”的 Result）、16 个检测方法挨个改返回值、SSL 三路放行（SSLContext.init 换 trust-all、平台 TrustManagerImpl 直通、OkHttp 的 Pinner 和 HostnameVerifier 全 no-op）。

spawn 模式注入，启动就挂。实测 root 真机上 16 项检测运行时全部报”干净”，5 条策略 isBlocked=false，一路无弹窗进到业务页。

踩坑记录：

  • MIUI 的 INSTALL_FAILED_USER_RESTRICTED → 用 root pm install-create 会话流式写入绕过
  • input tap 报 INJECT_EVENTS → root 权限执行
  • Git Bash 的 MSYS 路径转换会把 /data/... 改写成 Windows 路径 → MSYS_NO_PATHCONV=1
  • frida-server 17.x 在该机型 spawn 报 unable to pick a payload base → 降级 16.x 解决

路线 B：重打包静态免疫（更有意思）

Frida 版每次得挂 server，麻烦。我想要个不依赖注入工具的版本：

核心就一针：策略执行器的方法体整个换掉，直接返回”通过”——一个点废掉整个检测体系。顺带签名校验也放行了（毕竟换成了 debug 签名）。

验证够狠：frida-server 直接杀掉，确认进程列表里一个都不剩，冷启动重打包版从闪屏点到 OTP 页——零弹窗零崩溃。

两条路线的区别在于：A 说明检测能被绕，B 说明检测能被删。对厂商来说 B 才难受——16 项检测在发布包里就是个摆设。

5. 网络层：抓包链路的三次进化

发现环境矩阵

翻配置类挖出四个环境的完整地址表（dev/UAT/preprod/prod）。有个关键点：生产对某些地区的 IP 直接 WAF 403，UAT 裸奔。俩环境跑的是同一套代码——那就先在 UAT 把协议打通，再平移过去。

抓包链路进化史

代 方案 踩的坑
1 Wi-Fi 代理 → PC mitmproxy Windows 防火墙按程序放行（ Burp 有规则，python.exe 没有），手机到 PC 的 CONNECT 全部石沉大海
2 adb reverse USB 隧道 adb reverse tcp:8080 tcp:8080 + 手机代理指向 127.0.0.1:8080——绕开防火墙，链路秒通
3 手机直连（目标地区出口）+ Frida 协议日志 前两代都要过 PC 出口（撞 geo 墙）；最终方案是手机挂目标地区出口直连生产，Frida 在进程内把流量打到 stdout

第 3 代才算舒服：流量压根不碰 PC，监控点直接在进程里，geo 墙没意义了。

生产环境的 token 形态差异（意外收获）

实抓发现生产的 token 是 440 来个字符的 Base64 密文，UAT 那边却是标准 JWT。拿客户端的 AES key 去解——解不开，说明生产 token 是服务端加密好发下来的，客户端只管透传。脚本也照透传写就行，不用较劲。

Frida 钩 OkHttp 的 R8 坑

这块耗的时间最久，给后来人排雷：

  • jadx 反编译出的类名是重建的假名（如 okio.C3443i），运行时 Java.use 直接 ClassNotFoundException——R8 混淆后的真名要用运行时反射枚举字段类型才能拿到
  • 可靠的钩点：OkHttp 的 RealCall（execute/enqueue 两路都要钩，App 全走异步 enqueue）
  • 请求侧：反射遍历 call 对象字段找到 Request 实例，toString() 自带 method+url+headers 全量
  • 响应侧被 R8 深度内联：string()/charStream()/Gson(String)/JsonReader 四路钩子全试，只有 charStream 证明被走到（挂载计数命中），完整 body 最终靠 RPC 自发请求解决（见下）

6. 协议还原：登录、流水、详情、余额

6.1 这次的抓包为什么不是常规套路

常规套路是”手机挂代理 → PC 上的 Burp/mitmproxy 转发”。本次三个坑叠加导致它直接失效：

  1. 生产环境 geo 封锁：PC 出口 IP 直接 403，流量过了 PC 也到不了生产
  2. Windows 防火墙按程序放行：入站规则里只有 Burp 的 exe，mitmproxy 的 python 进程被静默丢弃——手机发的 CONNECT 石沉大海，且本地回环测试通过极易误判”链路正常”
  3. 就算抓包链通了，流量过 PC 出口依然撞 geo 墙

最终进化出三代方案，各有适用场景：

代 方案 适用
1 adb reverse USB 隧道：adb reverse tcp:8080 tcp:8080 + 手机代理指向 127.0.0.1:8080 防火墙死活不开时的通用解——流量走 USB 数据线，入站规则完全不参与
2 mitm 透明转投：mitmproxy addon 在请求钩子里改写目标（生产域名:端口 → 测试环境域名:443） 借道测试环境验证生产协议结构——手机端零改动，App 无感知，服务器返回的测试数据与生产同构（同代码）
3 进程内监控：手机挂目标地区出口直连生产，Frida 钩 RealCall 反射拿请求 + RPC 让 App 进程自发自读响应 生产实测终极形态——流量完全不经过 PC 网络栈，geo 封锁与监控解耦

一句话总结：常规抓包是”让流量经过我”，这次是”让流量绕过物理限制”+”把监控点内嵌进进程”。

6.2 解密也不是常规套路：TLS 明文之下还有两层

证书信任搞定只是过了第一层。TLS 明文底下还埋着两层自定义加密，而且俩策略互相打架：

① 列表接口与详情接口的加密策略打架

同一份数据：流水列表接口对余额、手机号返回 AES 密文；点进单笔详情接口——同样的字段明文裸奔，还附带交易时的出口 IP 和 GPS 坐标。同一个 App 的两个接口，加密策略自己打自己。安全结论：详情接口让列表侧的加密完全失去意义。

② AES 之下还有自定义 nibble 数字编码

用客户端硬编码的 AES key（CBC/全零 IV）解密列表接口的密文，出来不是可读文本——第一反应是 key 不对，实则是编码层：

  • 每个字节的低 4 位 = 一位数字
  • 0x1e = 小数点
  • 0x3a = 填充

手机号密文解出来逐位对上了，余额也对上了。到这才算真解密。说白了很多金融 App 的”加密”就是 key 写死在客户端 + 一个自己发明的可逆编码，两层都白搭。

③ 生产 token 的第三层

生产环境的 token 本身是服务端加密的密文（连 OTP 阶段的临时 token 都是），与测试环境的裸 JWT 完全不同源。用客户端 key 解不开 → 服务端侧加密。但客户端对所有 token 的处理都是”字符串透传”，协议脚本同样原样携带即可——不要试图在客户端解它，也不需要。

6.3 协议总貌

  • 全 REST POST + JSON body，字段名混淆为 b1~b14
  • 通用头仅 Version + 未登录 X-OAuth-Token / 登录后 X-Auth-Token
  • 响应统一信封：{status, message, token{...}, resultObj[]}——注意业务错误码在响应体的 status 字段里（401/444/445…），HTTP 状态码恒 200
  • 登录与流水链路无报文加密、无签名、无防重放（无 timestamp/nonce/HMAC）

6.4 双阶段登录协议

测试环境万能码：OTP 固定为 123456，任意手机号可登录——测试环境高危后门。

生产风控：同一手机号多次登录触发 24 小时封锁（专属错误码）。评估中真实踩中一次（测试号填错一位数字反复尝试），顺便把该频控机制记录在案。

单活跃会话：重新登录使旧会话的 access+refresh 同时作废——这就是抓包旧 token 调业务接口全 401 的真相。不是连接层指纹风控，纯粹的会话吊销语义。

6.5 流水协议：参数考古全程实录（踩坑最多的一个接口）

流水接口是整个项目磨得最久的一段——9 个混淆参数，每个都有一段故事。完整复盘：

坑一：测试环境拿到了”假成功”

最初在测试环境用静态推断的参数（b3="success"）调流水，返回 200 + SUC2001 + resultObj:[]——看起来一切正常。直到用真实账号在生产拉出有数据的流水才发现：同一参数在测试环境返回空列表不是”账号没交易”，是过滤值根本不对。测试环境的测试号恰好没有交易，把假阳性完美掩盖了。

教训：“200 带空列表”是参数考古里最大的假阳性。验证过滤参数只有一条标准——拿已知有数据的区间打，命中数对得上才算对。

坑二：401 之谜——花了一整天排查”连接层指纹风控”，答案是会话吊销

拿到生产有效 token 后调流水，清一色 401 "User is not Authorized"。第一反应是服务端有 TLS/HTTP 层指纹风控（金融 App 常见），于是做了完整的排查链：

  • 用 App 成功调用过的同一接口 + 同一 token → 依然 401
  • 补齐 OkHttp 的全部隐式头（Accept-Encoding/Connection/UA）→ 401
  • 甚至怀疑 HttpURLConnection 与 OkHttp 的 TLS 指纹差异

最后是个对照实验破的案：翻日志发现 App 自己发的请求里带的 token，跟我手里那串压根不一样——期间 App 重新登录过，服务端是单活跃会话，新登录一进来，旧的 access 加 refresh 全部作废。之前所有 401 就是这一个原因。之后每次拿到新 token 马上用，再没出过幺蛾子。

教训：排查服务端”风控”之前，先验证 token 的新鲜度与会话模型（单活跃/多活跃）——会话吊销的表现和风控一模一样。

坑三：token 一新，参数原形毕露

新 token 到手后一口气把 9 个参数全打一遍，静态推断的错误集中爆雷：

  • b3 状态：静态推断 "success" → 返回 200 空列表（假阳性）；挖过滤 UI 的 Fragment 源码找到真字面量 COMPLETED/FAILED/PENDING，命中数立即对上
  • b4 收支：推断 cr/dr → 空结果；从过滤弹窗 Fragment 里找到 DEBIT/CREDIT
  • b6/b7 日期：静态看到 SimpleDateFormat("dd-MM-yyyy") 就信了 → 三种日期格式全 500；回头细读代码发现那行格式化的是 Long.parseLong(filterStartDate)——毫秒时间戳字符串。再测还是空，又坑一轮：自己算毫秒值的时候时区没对，换 UTC 重算立刻命中
  • b8 卡：vpan 有效，内部卡 ID 返回专属错误码（白送的参数枚举信息）
  • b2 省略 → 500（必填确认）

一个日期参数来回坑了三轮：先是格式错，再是值错，最后发现自己算毫秒的时候时区都没对。每一轮都是靠”10 月明明有 2 笔交易必须命中”这个锚点逼出来的。

坑四：翻页语义

b1=21（跳过前 20 条）返回空 → 确认 b1 是绝对起始序号游标而非页码。首页 b1=1。

坑五（方法论总结）：流水参数考古的标准化流程

  1. 静态还原参数构造器（混淆 ViewModel 里的 addProperty 序列）
  2. 找 UI 调用点挖字面量（过滤选项的字符串常量藏在 Fragment/弹窗里，不在 ViewModel）
  3. 动态验证必须带已知答案：先用无过滤查询拿到基准数据，再逐个开过滤，命中数对不上=参数错
  4. 日期参数优先怀疑时间戳（毫秒/秒），格式化字符串其次
  5. 服务端错误码是免费的枚举提示：专属错误码（如”卡不存在”）说明参数类型对了值不对；通用 500 说明整个 body 结构不对

6.6 详情接口：加密策略不一致的重磅发现

列表接口对余额、手机号做 AES 加密（密文返回），但单笔详情接口 60+ 字段全明文：余额、手机号、交易时 IP、交易时 GPS 坐标全部裸奔。加密策略在同一个 App 的两个接口之间不一致——这是本次评估里最重的一条风险。

6.7 响应字段的 AES：自定义数字编码

见 §6.2②。key 写死在客户端 + 可逆的自定义编码——这套组合拳等于没加密，金融 App 里一抓一大把。

7. 转账协议：还原到哪一步、为什么停

转账链路静态还原做完了，PIN 算法也验证了，但资金接口没实测——红线，不碰。

这块最有价值的是 PIN 体系：

  • PIN block 算法：ISO-9564-0 Format-0（0+len+PIN+F* XOR 0000+卡号[3:15]）→ 3DES/ECB
  • 加密密钥（ZPK）硬编码在客户端——按金融规范 ZPK 应只存在于服务端/HSM。拿到 APK 的人可以离线生成合法 PIN block
  • 我用 Python 完整复现该算法，与 App 进程内实际调用对拍一致（同一输入产出相同密文）

转账接口的 body 结构从混淆参数构造器还原到字段级，但其中两个加密字段的明文语义（收款人/金额/PIN block 的分布）未验证——这块的完整还原需要一笔真实交易作为观测样本，属于破坏性/资金性验证，超出了授权范围。方法论上这叫”还原到可验证边界为止”。

8. SIM 绑定机制（三层强度）

层 机制 强度
登录 策略强制”SIM 存在” 弱——仅查存在，不验归属，换卡无阻
设备 设备绑定会话接口，返回加密的（手机号，设备ID）对 中——服务端记录手机号↔设备映射
移动支付注册 支付网络标准流程：用被绑定 SIM 真实发送一条短信到硬编码服务号码，验证串为加密拼接串 强——物理 SIM 参与验证，协议无法完全模拟

对协议自动化的影响：登录/查询全链路不受影响；只有移动支付注册环节存在物理 SIM 的硬依赖——这是整个 App 里唯一”协议绕不过去”的点。

9. 风险清单（给厂商的）

按严重程度排：

  1. 检测体系单点可绕：16 项检测集中在一个执行器，重打包移除后无任何二级校验；Frida 检测仅默认端口+包名
  2. PIN 加密密钥（ZPK）硬编码客户端——离线生成合法 PIN block
  3. 加密策略不一致：列表加密、详情明文（含 IP+GPS）
  4. 无请求签名/防重放：全协议可离线重放
  5. 测试环境万能 OTP：UAT 任意号 123456 登录
  6. QA 后门号码跳过全部本地检测
  7. 响应 AES 密钥客户端硬编码 + 自定义编码可逆
  8. token 生命周期长（60/180 天）+ 明文本地存储 + allowBackup=true

10. 方法论沉淀

最后留点能带走的：

  1. 判定壳的四证据链（dex 可读性/Manifest 入口/so 清单/字符串）——比单一看 so 文件名可靠
  2. svc 指令扫描证明 native 无隐蔽行为——比”没看到反调试字符串”硬一个量级
  3. 重打包免注入版优于 Frida 版——它验证的是”检测体系在发布形态下可被移除”，对厂商更致命
  4. 大 APK 反编译用 --no-res——只动 dex，资源原样，回编成功率高一个数量级
  5. split APK 重打包后所有 split 必须同 key 重签——新手必踩
  6. R8 混淆下 Frida 钩子：jadx 假名 ≠ 运行时真名，用反射枚举字段类型定位；同步/异步两个执行路径都要钩
  7. 协议参数验证：静态推断 + 动态实测缺一不可；”200+空列表”是假阳性重灾区，用已知数据交叉比对
  8. 抓包走不通时换监控点：网络层被 geo 墙挡 → 进程内 Frida 日志；响应被 R8 内联 → RPC 自发请求自己读
  9. 评估红线：资金接口还原到可验证边界为止，不碰真实资金流；用”自转 1 卢比”这类零损失样本作为可选观测手段（需客户同意）

完。所有细节已在授权评估框架下处理，测试数据已脱敏。
