解剖一个 Flutter 支付钱包：三层防护的失效史与全链路协议还原

发表于2026-11-02|更新于2026-11-03|逆向

本文为移动安全研究笔记，基于对某海外 UPI 支付应用的授权分析整理而成。应用名称、包名、域名、密钥等身份信息均已脱敏（下文统一以”目标 App”指代，涉及的第三方防护/SDK 组件一律以代号指代）。仅供安全从业者和开发者学习防御思路，请勿用于任何未授权场景。

0. 一句话剧透

一个银行级支付 App，把全部预算花在了客户端防护上——商业 RASP、热更新魔改引擎、自研检测层、TLS 钉扎，一层比一层唬人；而服务端对设备的信任模型几乎为零。于是逆向的结论可以用一句话概括：

客户端的每一道墙都可以被”焊死”而不是”翻越”，而服务端根本不在乎你从哪面墙外进来。

下面按解剖顺序展开。

1. 目标画像：一只”看起来很难啃”的 Flutter App

项目 情况（脱敏后）
应用类型 海外 UPI 支付/钱包（Google Play 正式包，~85MB）

Dart 版本 3.11.5 stable
热更新 Shorebird 魔改引擎
商业防护 某 RASP 商用引擎（下文简称 T 家）
登录通道 第三方 OTP 托管 SDK（下文简称 O 家）
埋点 Mixpanel + Datadog + Firebase 全家桶
Java 层 无自研业务，R8 短类名混淆，唯一自研类是 MainActivity（1300+ 行，全是安全检测）

第一眼的两个”意外”：

意外一：libapp.so 符号零混淆。strings libapp.so | grep package: 直接吐出全部 341 个 Dart 源文件路径，MVVM + Riverpod 的目录结构一览无余。Dart AOT 快照默认不混淆符号——开发者以为编译成 native 就安全了，其实等于把源码目录结构贴在了二进制里。

意外二：没有传统 DEX 壳。排查了全部国产加壳特征（secneo/ijiami/bangcle/jiagu），零命中；Application 类没有被替换，jadx 直接完整反编译 7443 个类。真正的”壳”由三层组成——这才是本文的主角。

2. 三层防护解剖

L1：Flutter AOT——伪加固

Dart AOT 把业务编译成 ARM 指令，常规 Java 逆向工具（jadx/Frida hook Java 层）瞬间失效。但 AOT ≠ 不可读：

  • 快照头明文记录版本与编译选项
  • 类名/方法名可读（见意外一）
  • 用 blutter 类工具可直接恢复近似源码的结构

唯一的拦路虎是 Shorebird 魔改引擎：它改了快照格式，blutter 解析时直接 SIGSEGV。热更新在这里意外扮演了反逆向角色——但只是把”恢复源码”变成”读汇编”，延缓而非阻断。

L2：T 家 RASP——真正的看门狗

市面上绕 RASP 的思路大多是”伪装”——让检测返回假数据骗过逻辑。本项目用的是更彻底的断路（circuit-breaking）：

不骗它，直接让它变瞎子聋子。检测代码还在跑，但采集不到数据、上报不了结果。

3.3 代理检测：焊死传感器

isProxyConfigured 的 MethodChannel 原生实现，插两行 smali 让它恒返回 false。从此挂系统代理、挂抓包工具，App 岁月静好。

断路哲学的妙处在于：不修改任何业务逻辑，请求报文与原版逐字节一致，服务端流量特征挑不出毛病；且不需要运行时挂钩（无 Frida 常驻），规避了大部分对抗检测。

4. TLS 钉扎与一次教科书级的网络考古

4.1 钉扎的位置

Flutter 引擎的 TLS 钉扎最终收敛到 libflutter.so 里的一个函数：ssl_verify_peer_cert。用 pattern 扫描定位偏移（本包为 0x94ac18），同样焊死：

补完这刀，任何中间人工具递来的假证书照单全收，App 流量全明文。

4.2 关键发现：Dart 根本不理系统代理

抓包时撞上一个诡象：mitm 代理模式下，O 家（Java 层 okhttp）流量全部可见，但 App 自己的 API 域名一个包都没有。App 也没报代理检测——因为检测已被焊死。

结论（真机 netstat 实锤）：

Dart 的 HttpClient 不读 Android 系统代理设置，永远直连。代理型抓包（mitm 代理模式、大部分”HTTP 抓包 App”的代理模式）对纯 Flutter App 的业务流量是天然失明的——你能看到的只是 Java SDK 们的流量，还以为抓全了。

能截到 Dart 流量的姿势只有三种：

  1. TUN/VPN 模式抓包工具（网络层截全部流量）
  2. Frida hook connect() 把 :443 改写进隧道
  3. iptables REDIRECT

这个认知值回票价——很多”抓不到 Flutter 包”的疑难杂症根因在此。

4.3 一个”两头堵”案例

测试机所在网络环境：挂代理 → OTP 服务商风控嫌机房 IP，掐；不挂 → 该服务商域名直连不通（ICMP 通是假象，TCP 443 根本不活）。两头堵。

解法是把设备流量经 USB 隧道借道另一台机器的家宽出口：adb reverse + 纯转发模式代理（--ignore-hosts ".*"，只做 CONNECT 隧道不解密）+ 系统代理指过去。发码一次成功。风控拉黑的从来不是”使用代理”，而是”出口 IP 信誉”——换到住宅 IP 立刻天下太平。

5. 登录协议全链路还原

MITM 全解密后，登录协议六步闭环（域名已脱敏）：

时效矩阵（实测，全部踩过坑验证的）

凭证 名义有效期 实际情况
OTP 一次有效 同码二刷 → 400，错误码 7114
idToken JWT 5 分钟 第④→⑤步必须秒级衔接，超窗服务端直接断连
authToken JWT 62 天 服务端会话闲置数小时即 403，名义有效期是摆设
secretMessage 每次登录新生成 短时效敏感操作凭证（配 ECDH）

两个还原协议的野路子

Spring Bean Validation 枚举法：对没抓到报文的端点（如转账），提交空 body——服务端校验器会把全部必填字段名和合法枚举值吐回给你（challengeType must be one of [OTP, EXTERNAL_AUTH, PIN, TOTP, PASS_THROUGH]）。一发入魂，等于服务端亲自给你写接口文档。

真转账的三道闸（全实测）：VPA 校验 → initiate（服务端下发 paymentID，客户端自造 UUID 被拒）→ authenticate。拦住协议转账的是 SIM 绑定闸：服务端要求账号曾在插着实体 SIM 的设备上完成过运营商网络侧静默认证——这关是物理的，协议层伪造不了 simDetail。

6. 动态分析踩坑集锦（每一条都是真实生产事故）

  1. MIUI 杀后台无痕：内存紧张时 LMK 连前台 App 静默杀（无 crash 无 FATAL，只有 am_proc_died）。App”无故消失”先查 /proc/meminfo，别冤枉补丁。
  2. MSYS 路径转换：Git Bash 下 adb push x /data/local/tmp/ 会被改写成 C:/Program Files/Git/data/... 推进设备的鬼目录，还报 Success。必须 MSYS_NO_PATHCONV=1。
  3. grep 吞输出：Git Bash 的 grep 在计数为 0 时不输出任何内容，会引发”流量为零”的误诊链。分析日志用 Python。
  4. OTP 一次性 + UI 不跳转：验证成功后 App 停在确认页不自动跳，用户干等 → 超窗 → 通用报错弹窗。三次登录失败有两次是这个 UX 坑，跟风控无关。
  5. extractNativeLibs=false：新版 App 磁盘上没有 lib/*.so，验 so 得拉 base.apk 解包。
  6. Android 16 的 PAC 指针认证：全开状态下裸 MOV/RET 桩实测兼容——ARM64 打桩没那么容易暴毙。

7. 防御视角：这个 App 输在哪

站在开发者的角度复盘，败因清单比技术细节更有价值：

  1. 单层信任模型。全部防护在客户端，服务端对请求的设备上下文零校验（实测：无设备绑定、无请求签名、无 IP 锁，纯脚本直调业务 API 全部 200）。客户端防护本质是”提高门槛”而非”边界”——门没修在墙上。
  2. RASP 事件单点出口。T 家引擎再精密，20+ 项检测的结果汇聚到一个 7 字节类的两个方法。单点即单杀。防护架构设计时应该让关键闸门（如签名校验失败）直接在服务端执行，而不是”客户端检测→上报→等服务端处置”。
  3. 符号不混淆的 AOT。libapp.so 的类名方法名全可读，等于给了攻击者一张活地图。Dart AOT 时代需要专门的符号混淆方案。
  4. 登录协议的时效设计。idToken 5 分钟是对的，但 authToken”JWT 62 天 + 服务端闲置几小时就废”的错位让长期自动化毫无障碍——会话寿命应该由服务端显式管理而非 JWT 名义有效期。
  5. 短信 OTP 的一次性依赖客户端自觉。同码二刷只靠服务端状态机拦——这个做对了（确实拦了），但 autoread 通道的 UI 停滞陷阱反而成了用户侧最频繁的故障源。

8. 结语

整个项目从拿到 APK 到协议级复现，静态两层、动态三台测试机、抓包四千条流量。最深的感受不是”防护多脆弱”，而是防护的错位：

客户端防护做到了 90 分（T 家引擎确实是商业级水准，断路它花了真功夫），服务端信任模型只有 20 分。而安全的有效水位，永远由最低的那块板决定。

对做攻防两边的人，这句话都值得细品。
