1. 题目初探

这是一个典型的 Android APK 逆向题，表面上是输入 flag 后点击按钮进行校验，但实际做了两层迷惑：

  1. 普通点击不会进入真正的 flag 校验逻辑。
  2. 真正的校验在 JNI 层完成，Java 里只能看到前置处理。

先看 APK 结构，可以发现：

  • 包名：com.example.mobile02
  • 入口 Activity：com.example.mobile02.MainActivity
  • 含有 native 库：libsecure_verify.so
  • 存在 classes.dex 和 classes2.dex

看到 native 库后，基本可以判断这题大概率是：

  • Java 层做格式校验和预处理
  • JNI 层做最终比对

2.2 表面按钮逻辑其实是烟雾弹

onCreate() 里给按钮绑定了点击事件。普通点击后会做这些事：

  1. 调用 SystemEnvironmentManager.updateState()
  2. 调用 SystemEnvironmentManager.prepareContext(...)
  3. 弹出 "Initializing Secure Handshake..." 提示
  4. 延迟执行 lambda$onCreate$0

继续往下看，lambda$onCreate$0 做的是：

  1. 读取输入框内容
  2. 调用 SecurityProvider.computeSecureHash(input)
  3. 弹出一个类似 "Signature Error: [xxxxxxxx] Mismatch" 的提示

这个逻辑看起来像校验，但实际上只是个干扰项，因为：

  • 它不会决定 flag 正误
  • 只是算了一个 MD5 相关的假结果并展示出来

所以如果只盯着按钮点击逻辑，会很容易被带偏。

2.3 真正入口是“长按”

SystemEnvironmentManager 里维护了一个 CLICK_TRIGGER 计数器。

逻辑大致是：

  • 每点击一次按钮，计数加一
  • 当点击次数达到一定值后，才会给按钮挂上真正的长按监听
  • 还额外判断了是否处于调试环境

也就是说，真实交互是：

  1. 先点按钮至少 3 次
  2. 再长按按钮
  3. 才会进入真正的 flag 校验

这个设计就是题目的一个坑点。

2.4 真正校验逻辑

长按事件最终会进入 SecurityCoreProcessor.onLongClick(View)。

  1. 从输入框读取字符串
  2. 调用 FlagValidator.isFormatValid(input) 判断格式
  3. 如果格式合法，再调用 FlagValidator.doFinalCheck(...)
  4. 根据返回值弹 success 或 fail toast

10. 这题的考点总结

这题整体不难，但坑点设计得比较完整，主要考这些内容：

  1. Android 事件流分析
  2. 识别假逻辑和真逻辑
  3. Java 层字节变换还原
  4. JNI 注册与 native 校验追踪
  5. 自定义 Base64 字典识别
  6. XOR/Fibonacci 流逆向

如果只看 UI 点击结果，很容易被假 hash 逻辑带偏；如果只把目标串当标准 Base64 去解，也会走歪。真正做通之后，会发现整条链其实比较工整，适合作为一道 Android + JNI 入门逆向题。
